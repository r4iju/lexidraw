# Private Apple sandbox Pro

Public Pro remains Coming soon and live charges remain disabled. Apple purchases and restore use #280's account allowance and #289's sandbox lifecycle contract. They never create a live entitlement, a second channel balance, rollover, a top-up or overage. Owner-approved private eligibility stays separate from payment status.

## Purchase safeguards

The production Settings → AI Power screen includes Apple sandbox availability, purchase/restore, pending/cancelled outcomes and shared status. Default debug builds, release/App Store builds and simulators cannot invoke `Product.purchase` or `AppStore.sync`. A dedicated internal DEBUG build must explicitly compile LexidrawKit with `LEXIDRAW_STOREKIT_SANDBOX`. Do not put that flag in shared release settings. This implementation deliberately leaves the flag absent from the checked-in project.

Even that build must match the fixed bundle identifier and obtain a StoreKit-verified `AppTransaction.shared` whose environment is sandbox, before fetching the monthly auto-renewable product or calling purchase/restore. Missing app transaction, authentication, product or server configuration yields an unavailable state. A product ID, account approval or UI label cannot establish sandbox distribution. No assumption about a future transaction's environment is made before purchase. The simulator and Xcode local-testing environment are disabled for this server flow. Apple-signed Sandbox data is required; Xcode/LocalTesting data never grants a server allowance.

Each action rechecks the authenticated server gate before StoreKit dispatch. The server generates a permanent account UUID, passes it as `appAccountToken`, and validates it on every transaction. Native verified transaction environment/product/token checks supplement server verification. Pending, cancelled, wrong-account and unverified results are not submitted as successful payments. A transaction is finished only after a valid server reconciliation result; rejected/uncertain transactions remain unfinished for updates or restore. The settings screen observes transaction updates while open and refreshes the account status after acceptance. Reopening, restoration and server notifications reconcile changes when the screen was closed.

## Server configuration and verification

Dedicated configuration only: `APPLE_SANDBOX_ENABLED=true`, `APPLE_SANDBOX_KEY` (a P-256 private key), `APPLE_SANDBOX_KEY_ID`, `APPLE_SANDBOX_ISSUER_ID`, and `APPLE_SANDBOX_SUBSCRIPTION_GROUP_ID`. There is no generic/live key fallback. Bundle `xyz.raiju.lexidraw` and product `xyz.raiju.lexidraw.pro.monthly` are fixed. The external product must be configured as the private monthly Pro plan. No external setup, credentials or product availability were inspected or changed in this task.

`pro.appleSandboxGate` is authenticated and returns an unavailable result to unapproved accounts or absent/unsupported configuration. `pro.appleSandboxClaim` accepts only a bounded signed transaction string. Account, token, group, lifecycle and allowance are never accepted from client fields. Gate configuration validation establishes local readiness, not proof that a remote key/product is configured or accessible; the internal build and verified app environment remain independent safeguards. Real external setup requires a separately authorized smoke test.

Apple's App Store Server Library 3.1.0 verifies ES256 JWS signatures, Apple certificate chain/OIDs, environment and bundle. Production trust is a fixed Apple PKI Root CA G3 (SHA-256 `63343abfb89a6a03ebb57e9b3f5fa7be7c4f5c756f3017b3a8c488c3653e9179`), with online certificate status checks enabled. Production never accepts test roots, disables verification, or selects the SDK's decode-only Xcode/LocalTesting modes. The test-only CA lives in a module imported exclusively by tests and opt-in local fixture harnesses. Its private keys are generated locally in a temporary directory and removed immediately.

The bounded sandbox transport exposes transaction/status reads only and has no production fallback. It uses the exact sandbox origin, numeric transaction identifiers, redirect rejection, no retries, a 1 MiB streamed response limit and a 10-second deadline including response bodies. Synthetic ES256 token signature/claims were verified locally. Apple SDK certificate/OCSP verification remains a separate external-access gate. A fresh current-status API read establishes freshness; signedDate records signing time and need not be within five minutes of the read. Future signed times and actual purchase/expiry bounds remain checked. Within the ledger write fence, independently retrieve the presented transaction and all current subscription statuses, verify their signed transaction/renewal data, and check exact transaction/original-group identity, account token, subscription group, product, purchased ownership (no family-sharing transfer), quantity, bounded paid interval, signed times and current status. Only the matching original transaction group is considered. Current renewal information maps auto-renew disablement to scheduled cancellation. Payment retry/grace stops new paid generation; verified recovery restores the existing balance. Expiry permits a strictly later paid renewal. A refund/revocation fences its own paid interval even when a restored cached receipt predates the refund or the current status reports a later renewal.

App Store Server Notifications V2 arrive at `/api/billing/apple-sandbox`. The bounded JSON boundary accepts only `signedPayload`; Apple SDK validation covers the outer notification and inner transaction/renewal signatures. Notifications trigger current sandbox status reads, not grants based on arrival order or notification type alone. Refund/revoke first independently resolve the affected transaction, persist its interval fence, then reconcile the current period. UUID replay records, period mappings and high-water marks suppress duplicate/reordered grants. Fixed errors exclude keys, raw provider errors, signed payloads and API envelopes from diagnostics.

## Durable accounting

Local migration 0030 adds permanent UUID account bindings and immutable historical lifecycle intervals. It seeds historical fences from existing revoked subscription rows and preserves migration 0029 and prior accounting. The existing source/original-group high-water mark enforces permanent original-group ownership. Each source/group/start maps to one shared period, including overlapping manual/Stripe/Apple purchases. Historical refund-before-grant fences remain authoritative after a later renewal advances the group. Payment failure before mapping attaches an overlapping allowance without minting credits; recovery cannot top it up. Outstanding operations still settle against their original reserved period.

Both web and iOS consume `pro.status`, including Apple source, lifecycle, cancellation, expiry, available/reserved credits and history. Web checkout availability and Apple readiness are separate fields. These authenticated tRPC methods do not change the generated REST/OpenAPI surface.
